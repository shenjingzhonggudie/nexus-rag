# MySQL索引优化

## 索引为什么能加速

MySQL 的 InnoDB 引擎用 B+ 树组织索引。B+ 树是一棵多叉平衡树，所有数据都存储在叶子节点，叶子节点之间用链表相连，非叶子节点只存索引键和指针。查询时从根节点逐层比较，每层能排除大量数据，因此一次查询只需要几次磁盘 IO 就能定位目标行。没有索引时，数据库只能全表扫描，一行一行地读磁盘比对，数据量大时慢得不可接受。索引的代价是占用额外的存储空间、拖慢写入速度，因为每次写入都要维护索引结构。所以索引不是越多越好，而是要在查询加速和写入开销之间权衡。

## B+ 树的特性

B+ 树相比普通 B 树有更适合数据库的特性。它的数据全部在叶子节点，非叶子节点只存索引键，因此每个节点能存更多键、树更矮、磁盘 IO 次数更少。叶子节点用双向链表相连，支持高效的范围查询和顺序遍历——范围查询定位到起点后，顺着链表就能读完整个区间，不需要回到上层节点。B+ 树是平衡树，所有叶子节点在同一层，因此任何查询的路径长度都一致，性能稳定。这些特性使 B+ 树成为关系型数据库索引的主流实现。

## 最左前缀原则

联合索引遵循最左前缀原则：只有查询条件从联合索引最左边的列开始连续使用，索引才能被完全利用。对 (a, b, c) 建联合索引，查询 a=1 能用索引，a=1 且 b=2 也能用，但单独查 b=2 或 c=3 则不能，因为索引是按 a 优先、再按 b、再按 c 排序的，跳过了最左列就无法利用这个顺序。理解最左前缀原则是设计联合索引的关键：把查询中最常一起出现、区分度最高的列放在前面，能最大化索引的利用率。建错列顺序的联合索引，等于白建。

## 索引失效场景

索引失效是最常见的性能坑。对索引列使用函数或运算会导致失效，如 where date(created_at) = '2026-01-01' 无法走索引，因为索引里存的是原始值，函数运算后的结果不在索引里。隐式类型转换同样致命：字符串列与数字比较时，MySQL 可能把整列转为数字，放弃索引。模糊查询的前导通配符 where name like '%abc' 也无法走索引，因为 B+ 树只能按前缀匹配。还有 OR 条件、负向条件、数据分布过差导致优化器主动放弃索引等。排查索引失效要靠执行计划，看实际走了哪个索引、扫描了多少行。

## 覆盖索引

如果查询所需的列都在索引中，就形成覆盖索引，可以直接从索引取数据而无需回表。覆盖索引是减少磁盘 IO 的重要手段，尤其适合高频查询。例如为 (name, age) 建联合索引，查询 select name, age from t where name='x' 时，name 和 age 都在索引里，直接从索引拿结果，不用回主键索引取整行。覆盖索引的设计思路是：把查询需要的列都放进索引，让索引本身就能满足查询。它的代价是索引更宽、写入开销更大，所以只对高频、关键的查询做覆盖索引优化。

## 回表的代价

回表指通过二级索引找到主键后，还要回主键索引取完整行数据。二级索引的叶子节点存的是主键值，不是完整行，所以查询需要的列如果不在二级索引里，就必须回表。回表次数多会显著增加 IO，因为每次回表都是一次随机磁盘访问。优化回表有两个方向：一是用覆盖索引避免回表，二是控制查询返回的行数，减少回表次数。回表本身不是问题，问题是大批量回表——返回几万行时，几万次随机 IO 会拖垮查询。这也是为什么要避免无谓的 select *，只查需要的列。

## 索引设计实践

索引设计要从查询出发，而不是从表结构出发。先梳理业务的高频查询，看它们的过滤条件、排序字段、返回列，再据此设计索引。区分度高的列优先建索引，区分度低的列建了也几乎没用。联合索引的列顺序要遵循最左前缀原则，把等值条件列放在前面、范围条件列放在后面。定期审视索引的使用情况，删除没有被查询用到却拖累写入的冗余索引。索引设计是持续演进的过程，业务查询模式变了，索引也要跟着调整。

## 慢查询的排查

慢查询定位要借助慢查询日志和执行计划。慢查询日志记录执行时间超过阈值的 SQL，是发现问题的第一入口。拿到慢 SQL 后，用 EXPLAIN 看执行计划：type 是不是 ALL 全表扫描、key 走没走索引、rows 预估扫描了多少行。结合这些信息判断是索引缺失、索引失效、还是查询本身设计不合理。排查慢查询不要只盯着单条 SQL，还要看它的执行频率——一条执行一万次的慢查询，比一条执行一次的超慢查询更值得优化。优化的优先级是：高频慢查询大于低频慢查询。
