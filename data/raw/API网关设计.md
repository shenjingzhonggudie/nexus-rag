# API网关设计

## API 网关的职责

API 网关是所有请求的统一入口，负责路由转发、鉴权、限流、日志等横切关注点。它把微服务的复杂性对客户端隐藏起来：客户端只需要和网关交互，不需要知道后端有多少服务、各自在哪。网关集中处理这些横切逻辑，避免了每个服务都重复实现鉴权、限流等能力。网关的定位是后端集群对外的统一门面，几乎所有请求治理能力都挂在这个门面上。网关设计的核心是职责的划分：哪些逻辑放网关，哪些放服务，划分不清会导致网关臃肿。

## 路由与转发

网关根据请求路径、方法等规则，把请求转发到对应的后端服务。路由规则要支持动态更新，因为后端服务的映射关系会变化。路由可以按路径前缀、精确路径、正则、请求头等多种维度匹配，灵活的规则能适应复杂的后端拓扑。转发的细节也很重要：请求头和响应头的透传、超时设置、重试策略，都影响后端的正确处理。路由转发是网关最基础的能力，也是性能的关键路径，转发逻辑要尽量轻量，避免成为瓶颈。

## 鉴权与限流

网关是统一的鉴权点，在请求进入后端前校验身份和权限。集中鉴权的好处是一致性好，所有入口的鉴权逻辑统一，不会出现各服务鉴权标准不一的情况。限流也在网关层实现，保护后端不被压垮。网关限流能挡住入口层面的过量流量，是保护后端的第一道防线。鉴权和限流放网关能大幅减少各服务的重复实现，但也要注意：网关只做粗粒度的鉴权和限流，细粒度的业务鉴权和限流仍需要服务层配合。

## 协议转换与聚合

网关可以做协议转换，如 HTTP 转 gRPC，让不同协议的客户端和服务端能够互通。聚合能力可以让网关同时调用多个后端，把响应合并后返回，减少客户端的请求次数。协议转换的价值在于屏蔽后端的技术选型，客户端统一用 HTTP，后端内部用什么都行。聚合的价值在于减少客户端的往返次数，尤其是移动端网络环境下。这两项能力让网关不仅是转发器，还承担了适配和编排的职责。

## 与反向代理的关系

API 网关和反向代理都有路由转发，但网关更偏业务，反向代理更偏网络。网关处理鉴权、聚合、协议转换等业务逻辑，反向代理处理请求转发、负载均衡等网络层逻辑。Nginx 这类反向代理也可以做一部分网关的事，比如限流和缓存，但复杂的业务编排能力不是反向代理的强项。实践中网关常架在反向代理之上，反向代理负责流量入口和负载均衡，网关负责业务层的治理。两者是不同层次的组件。

## 网关的性能考量

网关是所有请求的必经之路，性能至关重要。网关的转发路径要尽量短，鉴权、限流这些逻辑要高效，不能成为瓶颈。性能优化的手段包括：异步 IO、连接复用、缓存鉴权结果、限流计数器的本地化。网关的性能直接决定了整个系统的入口吞吐，一个慢网关会拖垮所有后端。同时网关也要做好自身的扩展性，流量增长时网关能水平扩展。网关的性能和扩展性设计，是整个 API 架构的地基。

## 网关的高可用

网关是单点入口，高可用是硬要求。网关本身要集群部署，前面挂负载均衡分散流量。网关的配置要能热更新，路由规则变化不停机。网关的故障影响面极大，一旦网关挂了，所有 API 都不可用，所以网关的稳定性设计要格外严谨。容灾方面，网关要有降级能力，后端全挂时至少能返回友好错误而不是连接超时。网关的高可用是系统可用性的基础，网关的可靠性投入怎么都不为过。

## 实践建议

网关设计的实践建议：职责要克制，只放横切关注点，业务逻辑留在服务层；路由规则要支持动态更新和灰度；鉴权和限流在网关做粗粒度，细粒度放服务层；网关要集群部署，高可用是底线；网关的性能要专门优化，它是入口瓶颈。网关的常见误区是过度膨胀——把太多业务逻辑塞进网关，网关变成新的单体。保持网关的轻量和专注，是网关设计的第一原则。
