# 容器网络配置

## 什么是容器网络

容器网络解决的是容器之间、容器与外部世界之间如何通信的问题。每个容器默认有自己独立的网络栈，看起来像一台独立的主机，但实际共享宿主机的物理网卡。容器网络的核心是让这些隔离的网络栈能够按规则互联互通。

## 网络命名空间

网络命名空间是 Linux 提供的一种隔离机制，它给每个容器一个独立的网络栈，包括自己的网络接口、路由表、防火墙规则和 socket。有了网络命名空间，容器里看到的网络接口、IP 地址就和宿主机以及其他容器完全隔离，这是容器网络一切能力的基础。网络命名空间虽然隔离，但并不是孤岛——它需要通过某种方式连接到外界。最常见的连接方式是一对虚拟以太网设备，也就是 veth 对：一端放在容器的网络命名空间里，另一端放在宿主机的网络命名空间里，两端像一个虚拟网线一样把容器和宿主机连起来。宿主机这一端通常会接到一个网桥上，这样多个容器就能通过网桥互通。理解网络命名空间，是理解容器网络的第一步，因为后面所有复杂的网络方案，本质上都是在不同的网络命名空间之间搭建通路、施加规则。网络命名空间也带来了排查上的特殊性：在宿主机上直接看到的网络状态，和容器里看到的是两套不同的视图，排查容器网络问题时，需要明确自己是在哪个命名空间里观察。网络命名空间的创建和销毁是容器生命周期的一部分：容器启动时，运行时创建命名空间并配置网络；容器停止时，命名空间连同里面的网络资源一起被回收。命名空间的隔离也不是绝对的，某些系统级的网络资源（比如 conntrack 连接跟踪表）是宿主机全局共享的，一个容器的大量连接可能影响其他容器。这也是为什么在大规模集群里，conntrack 表的容量会成为瓶颈。理解命名空间，还要理解它和宿主机网络栈的关系：容器里的网络请求，最终都要落到宿主机的物理网卡上发出去，所以宿主机的网络配置、防火墙规则、路由策略，都会对容器网络产生影响。

## veth 对

veth 对是一对成对出现的虚拟以太网设备，数据从一端进入，就会从另一端出来，可以理解为一条虚拟网线。在容器网络里，veth 对的一端放进容器的网络命名空间，另一端留在宿主机上，通常接到网桥。这样容器的网络流量就通过这条虚拟网线流到宿主机，再由宿主机转发。veth 对的创建和销毁由容器运行时管理，容器启动时创建、停止时销毁。

## 网桥模式

网桥模式是容器默认的网络模式。宿主机上有一个虚拟网桥，所有容器的 veth 一端都接到这个网桥上，形成一个二层网络，容器之间可以通过网桥直接通信。网桥模式简单高效，适合单机上的容器互通。在网桥模式里，网桥本身是一个虚拟的二层交换机，它根据 MAC 地址学习来决定把帧转发到哪个端口，所以同一网桥上的容器可以直接二层互通，不需要经过路由。网桥模式的一个重要细节是 NAT：容器访问外网时，源地址会被转换成宿主机的地址，所以外部看到的是宿主机的 IP 而不是容器的 IP。这也意味着外部无法主动访问容器，除非做了端口映射。理解网桥模式的二层转发和 NAT 这两点，就能解释大部分单机容器网络的行为。

## Host 与 None 模式

除了默认的网桥模式，容器还支持 host 模式和 none 模式。host 模式让容器直接使用宿主机的网络命名空间，容器不再有独立的网络栈，它看到的网卡、端口就是宿主机的网卡、端口。这种模式网络性能最好，因为少了一层虚拟化的开销，但代价是隔离性差——容器和宿主机共享端口空间，端口冲突、安全风险都随之而来，所以只在性能要求极高、且端口能严格控制的场景才用。none 模式则相反，容器有网络命名空间但没有任何网络接口，完全与外界隔离，通常用于对网络隔离要求极高的任务，或者由用户自己在容器里手动配置网络。理解这三种模式的关键，是理解它们在'隔离性'和'性能'之间做出的不同取舍：网桥模式取了中间值，host 模式偏向性能牺牲隔离，none 模式偏向隔离牺牲连通。选哪种模式，取决于业务对性能和隔离的具体要求。host 模式还有一个容易踩的坑：因为容器和宿主机共享网络命名空间，容器里用 localhost 访问的服务，实际是宿主机上的服务，这在某些应用场景下会造成意想不到的连通或冲突。none 模式则常被用作网络策略实验或自定义网络的起点，用户可以完全掌控容器里的网络配置。此外还有第四种模式叫 container 模式，让一个容器直接复用另一个容器的网络命名空间，通常用于 sidecar 场景，让辅助容器和主容器共享网络。这四种模式覆盖了从完全隔离到完全共享的整个光谱，理解它们的差异，是配置容器网络的第一步。

## Overlay 网络

Overlay 网络解决的是跨主机的容器通信问题。当容器分布在多台主机上时，它们不能简单地通过一个网桥互通，需要一种跨主机的组网方案。Overlay 网络通过隧道技术，把容器之间的二层流量封装在底层的三层网络里传输，让不同主机上的容器看起来在同一个网络里。Overlay 网络的好处是屏蔽了底层物理网络的差异，坏处是隧道封装和解封装带来额外的开销。Overlay 网络最常用的封装协议是 VXLAN，它把二层的以太网帧封装在 UDP 包里传输，从而让二层流量能跨越三层网络。VXLAN 的封装带来约几十字节的额外头部，对吞吐和延迟都有一定影响，但换来了跨主机的二层连通和良好的隔离性（不同租户可以用不同的 VXLAN 标识）。Overlay 网络的另一个好处是它不依赖底层物理网络的具体实现，只要底层三层网络是通的，Overlay 就能工作，这让它在混合云、多机房等异构网络环境下特别有价值。

## 端口映射

端口映射把容器内部的端口暴露到宿主机的某个端口上，让外部能够访问容器里的服务。用户请求宿主机的映射端口，流量再转发到容器内部。端口映射是单机容器对外提供服务最简单的方式，但它也带来端口管理的复杂度。端口映射的底层原理是 NAT：宿主机把某个端口的入站流量，通过目的地址转换转发到容器内部的端口。一个容易踩的坑是端口冲突——多个容器不能映射到宿主机同一个端口，这在服务多了之后需要人工协调。另外，映射到宿主机的端口会暴露到外部网络，如果没有额外的访问控制，等于把容器服务直接暴露了，存在安全风险。所以端口映射适合简单的单机场景，生产环境通常会配合负载均衡器，而不是直接暴露宿主机的端口。

## DNS 解析与服务发现

在容器环境里，服务的 IP 地址是动态分配的，容器重启后 IP 可能变化，所以不能靠写死的 IP 来通信，需要服务发现机制。Kubernetes 这类平台的做法是：给每个服务分配一个稳定的域名，容器之间通过域名访问，DNS 服务负责把域名解析到当前的 IP。这套机制让容器之间的通信从'依赖 IP'变成'依赖名字'，服务实例怎么变、IP 怎么漂移，调用方都不需要关心。DNS 解析在容器网络里也有自己的坑：DNS 缓存、解析超时、容器里 resolv.conf 的配置，都可能导致服务间通信出现诡异的问题。常见的故障是容器里的 DNS 查询超时，根因往往是 DNS 请求在集群里绕了一圈、或者 conntrack 表被 DNS 的并发查询打满。服务发现是微服务架构的基石，而 DNS 是服务发现最常见的实现方式，理解它就能理解大部分容器间通信的运作机制。服务发现还分服务端发现和客户端发现两种：服务端发现由负载均衡器统一维护服务实例列表，客户端只访问负载均衡器；客户端发现则把实例列表下发给客户端，由客户端自己选择实例。容器平台里常见的 Service 抽象，本质上是服务端发现的一种实现，它给一组 Pod 提供一个稳定的入口，背后的实例可以动态增减。理解服务发现，还要理解它和健康检查的配合——只有健康的实例才应该被注册到发现列表里，否则流量会打到已经挂掉的实例上。

## 网络策略

网络策略是对容器之间流量的访问控制，规定哪些容器可以和哪些容器通信、哪些端口可以访问。默认情况下，同一网络里的容器往往可以互相访问，这在多租户或安全敏感的场景下是有风险的，网络策略就是用来收紧这种默认开放的。网络策略通常以声明式的方式描述，由网络插件负责实施。策略的粒度通常到容器组和端口：可以规定某组容器只能访问某组容器的某几个端口，其余流量默认拒绝。设计网络策略时要遵循最小权限原则，先默认拒绝一切，再逐条放行必要的通信。但也要注意，网络策略默认拒绝之后，往往会出现'服务突然连不上了'的问题，因为漏掉了某些必要的通信路径，比如健康检查、监控采集、DNS 查询这些看似不起眼但必不可少的流量。所以落地网络策略要循序渐进，边放行边验证。

## 容器间通信

容器之间的通信有三种典型方式：同主机上的容器通过网桥直接通信，跨主机的容器通过 Overlay 网络或路由通信，容器和外部服务通过端口映射或负载均衡通信。三种方式对应不同的网络层级和适用场景。同主机容器的通信最简单，走网桥的二层转发，性能也最好；跨主机通信要经过 Overlay 或路由，多了一层转发；访问外部服务则涉及 NAT 和可能的负载均衡。理解这三种通信方式的差异，有助于在架构设计时选择合适的通信模式，也便于在排查时判断问题出在哪一层。

## 跨主机通信方案对比

跨主机容器通信的常见方案可以分成三大类。第一类是 Overlay 网络，比如 VXLAN，通过隧道把容器流量封装到底层网络，优点是简单、对底层网络要求低，缺点是有封装开销。第二类是直连路由，让每台主机的容器网段直接可路由，容器流量不经过隧道，性能更好，但对底层网络有要求，需要路由器或交换机支持相应的路由配置。第三类是纯三层方案，比如 Calico 的 BGP 模式，用路由协议在主机之间分发容器网段的路由，性能接近直连。选哪种方案，要看集群规模、底层网络能力、性能要求和运维复杂度。小型集群用 Overlay 省心，大型性能敏感的集群可能倾向直连路由或三层方案。没有绝对最优的方案，只有适合当前约束的方案。选择方案时还要考虑故障域和运维成本：Overlay 方案虽然简单，但出问题时隧道封装让抓包排障变得更复杂；直连路由方案性能好，但需要运维团队理解底层网络和路由协议。此外，方案的可扩展性也很关键，一个在几十个节点上跑得好的方案，未必能在几百上千节点的集群上继续稳定。所以跨主机通信方案的选择，本质上是在性能、简单性、可扩展性、运维复杂度这几个维度之间做权衡，而且这个权衡会随着集群规模的增长而不断变化。

## 网络性能考量

容器网络相比裸机多了一层虚拟化，性能会有一定损耗。损耗主要来自几个地方：veth 对的数据拷贝、网桥的转发、Overlay 的隧道封装。对于吞吐敏感或延迟敏感的业务，需要关注这些开销。优化手段包括使用 host 模式、选择直连路由方案、使用支持高速转发的网络插件、以及调优内核网络参数。在调优内核参数时，几个常用的方向是：增大 conntrack 表的容量、调整 TCP 缓冲区大小、优化网卡的中断亲和性。不过网络性能优化要建立在测量之上——先通过压测定位瓶颈在哪一层（是虚拟网卡、是网桥、还是隧道封装），再针对性地优化，否则盲目调参往往收效甚微。

## 网络安全

容器网络安全关注的是流量隔离、访问控制和防攻击。默认的开放网络在安全上是危险的，需要通过网络策略做最小权限控制。此外还要注意端口暴露的最小化、敏感服务不对外暴露、以及网络流量加密。容器网络的安全防线是多层的：网络策略做流量控制，镜像扫描防止容器本身携带漏洞，运行时安全防止容器逃逸，流量加密防止数据在传输中被窃听。任何一层都不能单独保证安全，需要多层配合。一个常见的安全疏忽是：内网流量默认不加密，认为内网是可信的；但在云环境和多租户场景里，内网同样可能被横向渗透，敏感流量的加密不应该省略。

## CNI 插件体系

CNI（容器网络接口）是一套标准，定义了容器运行时如何为容器配置网络的接口规范。任何实现了 CNI 接口的插件，都能被支持 CNI 的容器运行时调用，为容器分配网络。这套标准让网络方案和容器运行时解耦，用户可以在不同的网络插件之间选择，而不用改容器运行时。常见的 CNI 插件有 Flannel、Calico、Weave 等，它们在实现上差异很大，但都遵循同一套接口。CNI 插件的典型工作流程是：容器创建时，运行时调用插件的 ADD 命令，插件为容器分配 IP、创建网络接口、配置路由；容器销毁时，调用 DEL 命令回收这些资源。理解 CNI 的价值在于：它把'容器网络怎么实现'从'容器运行时怎么跑'里剥离出来，让两个复杂系统各自独立演进。CNI 规范本身很小，核心就是 ADD、DEL 两个操作和相应的配置格式，但正是这个小规范，催生了一个庞大的网络插件生态。CNI 插件除了负责分配 IP 和配置路由，还常常承担网络策略、带宽限制、IP 地址管理等更复杂的能力。选型时除了看插件的基本功能，还要看它的数据面实现（是隧道还是直连）、是否支持网络策略、对大规模集群的支持程度，以及社区的活跃度。CNI 插件一旦选定，后续迁移的成本不低，所以选型要慎重。

## Flannel 的工作方式

Flannel 是常见的 CNI 插件，它解决的是跨主机容器通信的问题。Flannel 的核心思路是给每台主机分配一个子网，主机上的容器从这个子网里拿 IP，跨主机的流量通过隧道封装转发。Flannel 配置简单、上手快，适合中小规模集群。它的主要短板是 Overlay 的封装开销和某些模式下的性能瓶颈。Flannel 支持多种后端，除了 VXLAN 之外，还有 host-gw 这种直连路由后端——它在主机之间直接建路由而不走隧道，性能更好，但要求主机之间二层可达。所以 Flannel 并不是只有 Overlay 一种玩法，可以根据底层网络条件选择不同的后端。这也说明，很多网络插件的'性能问题'其实取决于具体配置，而不是插件本身固有。

## Calico 的工作方式

Calico 是另一个常见的 CNI 插件，它默认使用纯三层路由方案，把容器流量当作普通 IP 路由处理，性能接近直连。Calico 还提供强大的网络策略能力，适合对性能和网络安全都有要求的集群。Calico 在纯三层方案之外，也支持 IPIP 或 VXLAN 封装，用于底层网络不支持直连路由的场景，所以它并不是只能直连。Calico 的网络策略基于 iptables 或 eBPF 实现，功能比 Flannel 丰富得多，但也因此配置更复杂。选 Calico 还是 Flannel，本质上是在'功能丰富'和'简单易用'之间做选择。

## 容器网络排障

容器网络出问题时，排障需要按层次逐步排查。第一步是确认容器本身是否有网络接口和 IP，可以在容器里看网卡和路由表。第二步是确认同主机的容器能否互通，这能区分问题是出在单机网络还是跨主机网络。第三步是确认 DNS 解析是否正常，很多'服务连不上'的问题其实是 DNS 解析失败。第四步是抓包，在 veth 对的两端分别抓包，看数据包到底在哪一层丢了。容器网络的排障难点在于网络状态分散在多个命名空间里，宿主机上看到的和容器里看到的不一样，需要养成'明确自己在哪个命名空间'的习惯。常见的坑包括：容器里没有默认路由、DNS 配置错误、端口被占用、网络策略误拦截、conntrack 表满等。掌握分层次的排查思路，比记住具体某个命令更重要。在实际排障中，还有几个高频的坑值得注意：容器能启动但服务起不来，可能是容器里的进程监听了错误的地址（比如只监听 127.0.0.1 而不是 0.0.0.0，导致外部无法访问）；容器之间时通时断，可能是 conntrack 表满了导致新连接被丢弃；DNS 解析偶发超时，可能是 DNS 请求的并发把 conntrack 打满，需要调整内核参数。排障时善用分层定位：先本机、再跨机、再 DNS、最后抓包，能把大部分网络问题快速圈定在一个小范围内。

## 容器网络的未来趋势

容器网络的发展趋势是更高的性能和更细粒度的安全。性能方面，出现了用 eBPF 加速数据面的方案，把网络处理从内核的通用路径移到可编程的高速路径。安全方面，服务网格把安全从网络层提升到应用层，做更细粒度的流量管理和加密。这些趋势都指向同一个方向：让容器网络在接近裸机性能的同时，提供更精细的控制能力。eBPF 的兴起尤其值得关注——它允许在内核里安全地运行自定义程序，网络处理可以绕过部分通用路径，直接在数据面做加速和可观测。过去网络策略、流量监控这些功能往往要依赖用户态的代理或内核模块，eBPF 让它们更高效、更灵活。当然，eBPF 也带来了更高的技术门槛，不是所有团队都能驾驭。容器网络的演进，本质上是把性能和灵活性这两个目标不断推向更高的水平。

## IP 地址管理

容器网络的 IP 地址管理（IPAM）解决的是'每个容器怎么拿到一个不冲突的 IP'的问题。在单机上，网桥会给容器分配一个子网内的地址；在跨主机的集群里，IPAM 要保证不同主机上的容器网段不重叠，这样流量才能正确路由。IPAM 的核心挑战是地址的规划、分配和回收：地址规划要预留足够的地址空间，分配要保证不冲突，回收要及时，避免地址泄漏。一个常见的坑是地址耗尽——当集群的容器数量超过了规划的地址空间，新容器就无法分配 IP，导致创建失败。所以在规划容器网段时，要预留足够的余量，并考虑地址的回收机制是否可靠。IPAM 还涉及固定 IP 的需求：有些服务（比如数据库）需要稳定的 IP，这就需要在动态分配之外，支持 IP 的保留和绑定。

## 负载均衡

容器环境里的负载均衡，把外部流量分发到多个容器实例上，是实现高可用和水平扩展的关键。负载均衡可以工作在四层（基于 IP 和端口）或七层（基于 HTTP 等应用协议），七层能做更细粒度的路由，比如按 URL 路径分发。容器平台通常内置了负载均衡能力，用户声明一个服务，平台就自动创建负载均衡器和转发规则。负载均衡还涉及健康检查、会话保持、连接复用等细节，这些都会影响实际的分发效果和用户体验。健康检查决定了不健康的实例能否被及时摘除，检查的频率和超时设置要平衡及时性和误判；会话保持（粘性）保证同一个用户的请求始终路由到同一个实例，对有状态的服务很重要；连接复用则减少了频繁建连的开销，提升吞吐。负载均衡的实现方式也分几种：有基于内核的、有基于代理的、有基于 DNS 的，各有优劣，选型时要结合流量规模和延迟要求。

## 服务网格

服务网格是在容器网络之上的一层基础设施，它把服务间通信的治理能力（负载均衡、熔断、重试、加密、可观测）从应用代码里剥离出来，下沉到网络层。服务网格的典型实现是 sidecar 模式：每个服务实例旁边跑一个代理，服务之间的流量都经过这个代理，代理负责执行治理策略。这样做的好处是应用不再需要自己实现这些复杂的通信逻辑，坏处是引入了额外的代理开销和运维复杂度。服务网格适合微服务数量多、通信治理需求复杂的场景；对于服务数量少、通信简单的团队，服务网格可能是过度设计。理解服务网格的关键，是理解它解决的是'服务间通信的横切关注点'——这些关注点和业务逻辑无关，但每个服务都需要，把它们集中到网络层统一处理，是一种架构上的分层。

## 网络带宽限制

在共享宿主机资源的场景下，需要对容器的网络带宽做限制，防止某个容器抢占过多带宽影响其他容器。带宽限制可以在容器网络接口上做流量整形，设定每个容器的上行和下行速率上限。带宽限制的难点在于精确的计量和控制，不同的网络插件对带宽限制的支持程度不同。对于多租户或混合部署的场景，带宽限制是保障公平性的重要手段。

## 容器网络与防火墙

容器网络和防火墙的关系需要仔细处理。宿主机上的防火墙规则会影响容器的网络流量，而容器平台自身的网络策略则是在应用层做访问控制。两者容易混淆：修改宿主机防火墙可能意外阻断容器流量，而只配置平台网络策略又忽略了宿主机层面的安全。实践中需要明确两者的职责边界，宿主机防火墙负责基础的网络安全，平台网络策略负责容器之间的细粒度控制，两者配合使用。

## 多网卡容器

默认情况下容器只有一个网络接口，但有些场景需要多网卡：比如把管理流量和业务流量分开、或者让容器同时接入多个网络。多网卡容器可以通过给容器配置多个网络接口实现，每个接口接入不同的网络。多网卡的复杂度在于路由配置——需要明确哪些流量走哪张网卡，否则可能出现流量走错网卡的问题。多网卡常用于网络隔离要求高的场景，比如存储网络和管理网络分离。

## IPv6 支持

随着 IPv4 地址的枯竭，容器网络对 IPv6 的支持越来越重要。容器网络方案需要支持 IPv6 地址的分配和路由，以及 IPv4 和 IPv6 双栈的运行。IPv6 在容器网络的落地还面临一些兼容性问题，但它是不可回避的趋势。

## 网络隔离的层次

容器网络的隔离可以从多个层次理解：最底层是网络命名空间，提供进程级的网络栈隔离；往上是网络策略，提供容器之间流量的访问控制；再往上是服务网格，提供应用层的流量治理。不同层次的隔离解决不同的问题，也带来不同的开销。理解隔离的层次，有助于根据安全需求选择合适的手段，而不是一味堆叠所有层次的隔离。

## 容器网络监控

容器网络的监控是保障网络稳定运行的基础。需要监控的指标包括：网络的吞吐量、延迟、丢包率、连接数、conntrack 使用率等。吞吐量反映网络是否成为瓶颈，延迟反映用户体验，丢包率反映网络质量，连接数和 conntrack 使用率则关系到连接的稳定性和表容量。监控不仅要采集指标，还要能快速定位问题：当网络出现异常时，要能追溯到是哪个容器、哪个连接、哪条链路出了问题。容器网络监控的难点在于网络状态分布在多个命名空间和多个主机上，需要统一的采集和聚合。有了充分的监控数据，网络问题才能从'事后救火'变成'提前预警'。

## 网络故障的预防

容器网络故障很多是可以提前预防的。预防的手段包括：做好地址规划避免地址耗尽、设置合理的 conntrack 参数避免连接表打满、配置 DNS 缓存减少解析压力、对网络插件做容量评估避免成为瓶颈。预防还需要建立变更的评审机制，网络配置的变更往往影响面广，需要谨慎评估。预防的成本通常远低于故障发生后的排查和恢复成本。预防还需要建立监控和告警的闭环：当网络的某些指标出现异常趋势时，能在故障真正发生之前就发出预警。比如 conntrack 使用率持续上升，就可能是连接泄漏的前兆，提前干预能避免连接表打满。把网络的可观测性做到位，是预防的前提——看不到问题，就谈不上预防。

## 网络插件对比总结

主流的容器网络插件各有侧重：Flannel 简单易用、适合中小集群；Calico 性能好、网络策略能力强；Cilium 基于 eBPF、主打高性能和可观测性。选型时没有唯一的正确答案，要根据集群规模、性能要求、安全需求、团队能力综合判断。一个实用的建议是：先明确自己的核心需求是什么，再选最匹配的插件，而不是盲目追求功能最全的那个。

## 网络故障的排查工具

容器网络排查有几个常用工具：在容器里看网卡和路由表（ip addr、ip route）、测试连通性（ping、telnet、curl）、抓包（tcpdump，在 veth 两端分别抓）、以及查看 DNS 解析（nslookup）。这些工具配合分层次的排查思路（先本机、再跨机、再 DNS、最后抓包），能定位大部分网络问题。抓包是排查网络问题的终极手段，当其他方法都定位不了时，抓包看数据包到底在哪一层丢的，往往能找到答案。

## 小结

容器网络的核心是网络命名空间、veth 对和网桥这三个基础构件，其余复杂的方案都是它们的组合与延伸。理解基础构件，就能理解各种网络方案的本质差异。
