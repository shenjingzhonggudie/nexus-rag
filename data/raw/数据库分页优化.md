# 数据库分页优化

## 深分页问题

limit offset 在偏移量很大时性能急剧下降，这是分页最经典的问题。数据库执行 limit 100, 20 时，要先扫描并丢弃前 100 行，才能返回后面 20 行。offset 越大，扫描的无效数据越多。当 offset 到几十万甚至上百万时，每次查询都要扫描海量数据，性能不可接受。深分页的根源是 offset 的本质：它要求数据库从头开始数，数到 offset 才返回。这个特性决定了 offset 分页天然不适合深翻页场景，翻得越深越慢。

## 游标分页

游标分页用上一页最后一条记录的主键作为起点，避免 offset 扫描。查询时用 where id > last_id limit 20，直接从 last_id 之后取数据，不需要扫描前面所有行。游标分页适合无限滚动的场景，如信息流的持续加载。它的局限是要求排序字段唯一且有序，通常是自增主键或时间戳；而且不能跳页，只能顺序翻页。游标分页牺牲了跳页的灵活性，换取了深分页的高性能。对大多数无限滚动场景，这个交换是划算的。

## 分页的索引配合

分页查询要有合适的索引支撑，尤其是排序字段和过滤条件。分页通常配合 order by，如果排序字段没有索引，数据库要先全量排序再取分页，性能极差。过滤条件也要走索引，否则分页退化成全表扫描。分页加排序加过滤的组合，需要一个复合索引覆盖，索引的列顺序要符合最左前缀原则。索引缺失时分页性能问题会被放大，因为分页本身就要扫描，扫描的每一行如果还要回表或排序，代价就更高。分页优化的第一步往往是检查索引是否合理。

## 大数据量分页

数据量极大时，单纯分页也解决不了问题，需要配合分库分表、数据归档等手段，把单表数据控制住。分页的性能上限由单表数据量决定，表越大，深分页越慢。分库分表把数据拆散，每个分片的数据量可控，分页在分片内执行性能就好。数据归档把冷数据移出主表，主表只保留热数据，分页范围自然缩小。大数据量分页的根本思路是：控制分页扫描的数据范围，而不是在越来越大的表上硬分页。

## count 的性能问题

分页通常要显示总数，count 查询在大表上也可能成为瓶颈。count 在没有索引覆盖时要扫描全表，数据量大时很慢。优化 count 的思路：一是用缓存保存总数，定期刷新；二是如果不需要精确总数，用估算值；三是用索引覆盖优化 count 的执行。很多分页场景里，总数的精确性并不重要，用户关心的是能翻到后面几页，而不是总数精确到个位。对 count 的优化要结合业务对精确性的要求，避免为一个精确的总数付出全表扫描的代价。

## 深分页的改写

深分页场景优先用游标或改写查询，从根上减少扫描量。一种改写是子查询法：先 limit offset 查出主键，再回表取数据，减少回表开销。另一种是 join 法：用主键的延迟关联，先在小范围内找到目标主键，再关联取全量数据。这些改写的共同思路是让数据库先在一个小范围上定位，而不是在大范围上扫描后丢弃。不过改写的收益有限，真正的深分页问题还是要靠游标分页或限制跳页深度来解决。产品层面也可以限制用户能翻到的最大页数。

## 分页与排序的稳定性

分页配合排序时要注意排序的稳定性。如果排序字段有重复值，用 offset 分页可能出现同一行在相邻页重复出现或遗漏。这是因为重复值的相对顺序不稳定，两次查询的排序结果可能不同。解决方法是给排序加上唯一字段作为次级排序键，比如 order by create_time desc, id desc，保证排序完全确定。游标分页也依赖排序的稳定性，last_id 要能唯一定位位置。排序稳定性是分页正确性的前提，不稳定会直接导致数据错乱。

## 实践建议

分页优化的实践建议：避免用户直接跳转到极深的页，产品上限制翻页深度；深分页场景优先用游标分页或改写查询；分页查询要配合合理的索引，尤其是排序和过滤字段；大数据量时配合分库分表和归档控制单表规模；count 不要追求过度精确，能估算就估算。分页优化的核心是从根上减少扫描量，而不是在 offset 上做文章。理解 offset 分页的本质局限，才能在合适的场景选择合适的分页方式。
