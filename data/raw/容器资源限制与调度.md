# 容器资源限制与调度

## 什么是容器资源限制

容器资源限制是对容器能使用的 CPU、内存等资源的约束，防止单个容器无节制地占用资源、影响同节点的其他容器。资源限制是容器隔离性在资源维度的体现，是共享宿主机资源的前提。

## CPU 限制的机制

容器对 CPU 的使用限制，核心机制是 CPU 配额。在 Linux 里，这是通过 cgroup 的 CPU 子系统实现的，可以给容器分配一个 CPU 权重或一个硬性的 CPU 上限。CPU 权重决定的是在 CPU 争抢时容器能分到多少比例，它是有弹性的——当宿主机 CPU 空闲时，容器可以超过权重使用；CPU 上限则是硬限制，容器无论如何不能超过这个上限。理解这两者的区别很重要：权重适合大多数业务，因为它允许业务在空闲时用满 CPU；上限适合对延迟特别敏感、或者需要严格计费的场景。一个常见的坑是：给容器设了 CPU 上限后，业务的延迟明显变高，原因可能是上限设得太低，导致业务的高峰请求排队等待 CPU。所以 CPU 限制的设置，要基于对业务 CPU 使用模式的了解，而不是拍脑袋定一个数。除了 CPU 配额，还有一个相关的概念是 CPU 时间片和 cfs 周期：内核通过 cfs（完全公平调度器）把 CPU 时间按权重分给各个 cgroup，配额机制则是在此基础上加一个硬上限。理解 CPU 配额和 CPU 权重的区别，是设置 CPU 限制的核心——权重是软性的、可超用的，配额是硬性的、不可超用的。对于绝大多数在线业务，用权重（request）就够了，不需要硬性上限（limit），因为硬上限会让业务在需要 CPU 时被卡住。

## 内存限制与 OOM

内存限制是容器资源限制里最容易出事的一项，因为内存超限的后果是 OOM——进程被直接杀掉。容器设了内存上限后，一旦内存使用超过上限，内核的 OOM killer 就会介入，优先杀掉容器里占用内存最多的进程，整个容器可能随之崩溃。所以内存限制的设置要特别谨慎：设得太小，业务频繁 OOM；设得太大，又失去了限制的意义。一个实用的建议是：给内存限制留足余量，同时监控业务的实际内存使用，逐步调整到一个合适的值。还要注意，内存的使用是波动的，业务高峰时的内存可能远高于平时，所以不能按平均使用来设限制，而要看峰值。理解内存限制和 OOM 的关系，是避免容器莫名重启的关键。OOM 发生时的表现，往往是容器突然退出、重启，日志里看不到明确的错误，这就让问题变得难排查。要确认是不是 OOM，可以看平台的容器事件或内核日志，通常会留下 OOM 的痕迹。预防 OOM 的手段，除了合理设置内存限制，还包括监控内存使用趋势、在接近上限时提前告警，以及给业务加内存保护机制（比如 JVM 的堆上限）。内存问题一旦发生，往往影响面大，所以防患于未然特别重要。

## 资源请求与限制

资源请求和资源限制是两个不同的概念。请求是容器声明自己需要的资源量，调度器据此判断节点有没有足够资源来调度这个容器；限制是容器实际能使用的资源上限。请求通常小于或等于限制，请求决定调度，限制决定运行时的约束。只设请求不设限制，容器可能超用资源；只设限制不设请求，调度器无法正确判断节点的承载能力。两者配合使用，才能既保证调度合理、又保证运行受控。

## CPU 抢占与吞吐

在多容器共享宿主机 CPU 的场景里，CPU 抢占是影响业务性能的重要因素。当宿主机 CPU 被多个容器争抢时，每个容器实际获得的 CPU 时间取决于它的权重，权重低的容器可能被频繁抢占，导致延迟抖动。对于延迟敏感的业务，CPU 抢占带来的抖动可能是致命的，因为一个请求本来 10 毫秒能处理完，被抢占后可能变成 100 毫秒。应对 CPU 抢占的手段包括：提高延迟敏感业务的 CPU 权重、使用 CPU 亲和性把业务绑定到特定核、或者给节点做隔离让关键业务独占。理解 CPU 抢占对延迟的影响，是容器环境下做性能调优的重要一环。CPU 抢占的问题在混部场景尤其突出：把延迟敏感的在线业务和对 CPU 消耗大的离线任务混在一个节点上，离线任务会抢占在线业务的 CPU，导致在线业务延迟抖动。解决混部的 CPU 争抢，除了调权重，还可以用更精细的资源隔离手段，比如把在线业务和离线任务调度到不同的 CPU 池，或者用 QoS 分级。混部是提升资源利用率的重要手段，但前提是能控制住 CPU 抢占带来的干扰。

## 资源超卖

资源超卖是指节点上所有容器的资源请求之和，超过了节点的实际资源。超卖能提高资源利用率、降低成本，因为不是所有容器都会同时用满它们的请求；但超卖也有风险——当容器同时用满资源时，节点会过载，触发驱逐或 OOM。资源超卖是一个资源利用率和稳定性之间的权衡，超卖比例要基于对业务资源使用模式的了解来设置，盲目超卖会导致稳定性问题。

## 资源配额

资源配额是在命名空间级别对资源总量的限制，防止某个团队或项目无节制地消耗集群资源。资源配额可以限制 CPU、内存的总量，也可以限制对象的数量（比如 Pod 数、卷数）。资源配额是集群多租户管理的基础，让不同团队在资源使用上互相隔离。配额的设置要结合团队的实际需求，过紧会影响开发效率，过松又失去了管控的意义。

## 命名空间级配额

命名空间级配额和资源配额是同一层级的管控，它把资源的总量约束在命名空间范围内。一个命名空间下的所有容器，其资源请求之和不能超过配额。这样集群管理员可以给每个团队分配一个命名空间和相应的配额，团队内部自行分配资源。命名空间级配额是集群资源治理的重要工具。

## 调度器的作用

调度器负责决定每个容器应该运行在哪个节点上。它根据容器的资源请求、节点的可用资源、以及各种调度约束，选择一个合适的节点。调度器是集群资源分配的核心，它的决策质量直接影响集群的资源利用率和稳定性。

## 调度策略与算法

调度器的决策过程通常分两个阶段：过滤和打分。过滤阶段排除掉不满足条件的节点，比如资源不足的、有污点不允许调度的、不满足亲和性规则的；打分阶段对剩下的节点按某种策略打分，选得分最高的节点。打分策略会综合考虑资源均衡、亲和性、节点负载等因素，不同调度器的打分算法不同。理解调度器的两阶段决策，有助于理解为什么容器会被调度到某个节点、以及如何通过调度策略影响调度结果。调度策略的选择往往是一个权衡：是优先打散负载（让容器分散到不同节点）、还是优先聚拢（让相关容器挤在一起减少网络延迟），取决于业务的具体需求。调度策略还可以通过自定义调度器来扩展，比如针对特定类型的工作负载做专门的调度逻辑。但自定义调度器是一个复杂的工程，需要权衡维护成本和收益。对大多数团队来说，用好调度器内置的过滤和打分规则、配合亲和性、污点等约束，已经能覆盖大部分需求，不必急于自研调度器。

## 亲和性与反亲和性

亲和性和反亲和性是调度约束，用来控制容器之间的放置关系。亲和性让容器尽量调度到一起（比如让应用和它的缓存靠近），反亲和性让容器尽量分散（比如让同一个服务的多个副本分布在不同节点，避免单点故障）。亲和性和反亲和性能实现更精细的调度控制，但也增加了调度的复杂度。

## 污点与容忍

污点和容忍是一套反向的调度机制：节点可以设置污点，表示拒绝某些容器的调度；容器可以设置容忍，表示能接受带有特定污点的节点。污点常用于节点隔离，比如给专门跑 GPU 任务的节点打上污点，只有声明了容忍的 GPU 容器才能调度上去。污点和容忍是资源隔离和专用化的常用手段。

## 资源碎片化

资源碎片化是指节点上的资源被分割成许多小块，虽然总量足够，但没有一个节点能容纳下新的大容器。碎片化会导致资源利用率下降——明明集群还有资源，新容器却调度不上去。资源碎片化是动态调度的一个固有问题，缓解手段包括：合理设置资源请求的大小、定期整理（重新调度容器）、以及使用更智能的调度策略。

## 节点压力驱逐

当节点的资源（内存、磁盘）紧张时，平台会触发压力驱逐机制，把一些容器驱逐出节点，以释放资源。内存压力驱逐和 OOM 不同：驱逐是平台主动的、有策略的，OOM 是内核被动的、突然的。驱逐通常会优先驱逐资源请求和实际使用差距大的容器、或者优先级低的容器。驱逐对被驱逐的业务是有影响的——容器被强制迁移，可能造成短暂的不可用。理解节点压力驱逐，有助于理解为什么容器会突然被迁移，以及如何通过合理设置资源请求来降低被驱逐的概率。驱逐的触发条件通常是内存或磁盘的硬性阈值，当节点资源低于安全水位时，平台会按优先级从低到高驱逐容器。被驱逐的容器会在其他节点上重建，但这期间业务可能短暂中断。为了减少被驱逐的概率，业务应该设置合理的资源请求（这样调度器会把它放在资源充足的节点）、避免内存无节制增长（防止触发内存压力）、以及给关键业务设置更高的优先级。

## 资源监控

资源监控要关注容器的 CPU、内存、磁盘、网络的实时使用情况，以及和请求、限制的关系。监控能发现资源使用异常、接近限制的容器、以及节点的资源压力。资源监控是容量规划、故障排查、资源优化的基础。

## 资源的合理设置

给容器设置合理的资源请求和限制，是容器运维的一项基本功。设置的原则是：基于实测数据，而不是猜测。可以先不设限制，让容器跑一段时间，观察它的实际资源使用，再据此设置请求（略高于平均值）和限制（略高于峰值）。资源设置不是一次性的，业务变化后要重新评估。一个常见的错误是资源请求设得过大，导致节点明明有资源却调度不上新容器；或者限制设得过小，导致业务频繁 OOM。合理设置的最终目标，是让资源利用率高、同时业务稳定运行。这个目标听起来简单，实现起来却需要持续的努力：要监控、要分析、要调整，循环往复。资源设置没有'设一次就完事'这回事，业务在演进，资源的使用模式也在变，过去合理的设置，今天可能就不再适用。把资源设置当作一个持续的运维动作，而不是一次性的配置任务，是做好这件事的关键心态。

## 资源限制的常见误区

资源限制有几个常见误区。一是只设内存限制不设 CPU 限制，或者反过来，导致某一维资源失控。二是把请求和限制设成一样的值，失去了请求的弹性。三是设了限制就再也不调整，业务变化后限制过时。四是盲目追求高资源利用率，把超卖设得过高，牺牲了稳定性。五是忽略了存储和网络的资源占用，只关注 CPU 和内存。

## cgroup 的机制

容器资源限制的底层实现是 cgroup（控制组），它是 Linux 内核提供的一套机制，用来把一组进程的资源使用约束起来。cgroup 把 CPU、内存、IO 等资源都抽象成可配额、可统计的对象，容器运行时就是通过给每个容器创建独立的 cgroup，来实现资源隔离。理解 cgroup 有助于理解资源限制的行为细节：比如 CPU 限制为什么是有弹性的、内存限制为什么触发 OOM。cgroup 也分 v1 和 v2 两个版本，v2 统一了资源控制接口，是目前的主流。对大多数用户来说，cgroup 是透明的，但了解它的存在，能帮助理解某些资源行为的底层原因，比如为什么容器里看到的 CPU 数量和宿主机的实际核数不同。cgroup 的资源统计和限制，是理解容器资源监控数据的基础——容器里看到的资源使用，是 cgroup 视角的统计，和宿主机全局的统计口径不同。这也是为什么容器监控数据有时会和宿主机监控对不上。掌握 cgroup 的基本概念，能少很多对资源数据的困惑。

## CPU 亲和性

CPU 亲和性是把容器绑定到特定的 CPU 核上运行。它的好处是减少 CPU 缓存的失效，提升性能，尤其是对延迟敏感、或者有 CPU 缓存局部性要求的业务。坏处是绑定了特定核后，调度的灵活性下降，可能造成 CPU 核的利用不均。CPU 亲和性通常用于高性能计算或实时性要求高的场景，普通业务一般不需要。

## 内存与 page cache

容器里看到的内存，除了进程实际使用的内存，还包括 page cache——内核用来缓存文件数据的部分。page cache 的归属在容器内存统计里常常引起困惑：容器读文件产生的 page cache 算不算容器的内存？在 cgroup 的统计里，page cache 是算在容器头上的，所以一个读大量文件的容器，内存统计会偏高。理解 page cache 的归属，有助于正确解读容器的内存监控数据。

## 资源限制与 JVM

Java 应用在容器里的资源限制，是一个经典的坑。早期 JVM 不感知容器，它默认按宿主机的内存和 CPU 来设置堆大小和 GC 线程数，结果容器设了 1G 内存上限，JVM 却以为有几十 G，直接把容器内存打爆、触发 OOM。后来的 JVM 版本引入了容器感知能力，能读取 cgroup 的限制来调整默认参数。但即使如此，JVM 在容器里的堆大小设置仍然要显式配置，不能完全依赖默认。一个常见的实践是：把 JVM 的堆大小设为容器内存上限的一个比例（比如 75%），给元空间、线程栈、page cache 等留出余量。理解 JVM 和容器资源限制的交互，能避免 Java 应用在容器里频繁 OOM 的经典问题。这个问题的根源，是 JVM 和应用容器化之间的认知错位：JVM 管理自己的堆内存，而容器平台管理整个容器的内存，两者需要一个清晰的边界。除了堆大小，JVM 的 GC 线程数、元空间大小、线程栈大小也都会消耗容器内存，设置时要一并考虑。Java 应用容器化时，把 JVM 参数和容器资源限制对齐，是避免内存问题的第一步。除了内存，JVM 的 CPU 相关参数也要注意：JVM 默认按宿主机的 CPU 核数来设置 GC 线程数、线程池大小，容器里 CPU 被限制后，这些默认值就偏大了，可能导致过多的线程竞争有限的 CPU。所以 Java 应用容器化，除了堆大小，还要关注和 CPU 核数相关的参数。理解 JVM 的资源感知机制，是 Java 应用在容器里稳定运行的前提。

## 容器资源与性能测试

给容器设置资源限制前，应该做性能测试，了解业务在不同资源下的表现。测试要观察业务在资源紧张时的行为：CPU 受限时延迟如何变化、内存受限时是否 OOM。性能测试的数据是设置资源请求和限制的依据。测试时要注意模拟真实的负载，包括峰值负载，因为资源限制的问题往往在高峰时才暴露。

## 节点的资源预留

节点上除了容器，操作系统本身和平台组件（kubelet、容器运行时、监控代理）也要占用资源，所以在调度时，节点的资源不能全部分配给容器，要预留一部分。这部分预留的资源如果不考虑，会导致节点实际过载。资源预留通常在平台层配置，为系统组件保留一定的 CPU 和内存。合理的资源预留是节点稳定运行的保障。

## 调度的可扩展性

随着集群规模的扩大，调度器的性能也面临挑战。大规模集群里，调度器要在短时间内为大量容器做出调度决策，调度延迟会直接影响容器的启动速度。调度的可扩展性优化包括：调度算法的优化、并行调度、以及分级调度。调度器的可扩展性是超大规模集群的重要课题。

## 资源限制的演进

容器资源限制的能力在不断演进。从最初只支持 CPU 和内存，到后来支持 IO、网络带宽、GPU 等更多资源的限制，资源限制的粒度越来越细。这背后是异构计算（GPU、FPGA）和多租户场景的需求推动。理解资源限制的演进，有助于理解容器平台的资源管理能力边界。

## 有状态与无状态的资源差异

有状态应用和无状态应用在资源使用模式上有显著差异，这影响了它们的资源设置。无状态应用通常是水平扩展的，单个实例的资源使用相对稳定，资源请求和限制可以设得比较一致。有状态应用（比如数据库）的资源使用波动大、且对资源敏感，内存不足会直接导致性能下降或 OOM，所以它们的资源设置要更谨慎，通常要留更大的余量。此外，有状态应用往往需要绑定持久卷，这又涉及存储资源的调度。理解有状态和无状态应用的资源差异，才能在设置资源时做出正确的决策。有状态应用的资源设置还有一个特殊点：它的扩缩容不像无状态应用那样随意，因为数据是持久化的，扩缩容往往涉及数据的迁移和复制。所以有状态应用的资源规划，要和应用的数据架构一起考虑，而不是孤立地看 CPU 和内存。这一差异，也解释了为什么有状态应用的容器化难度远高于无状态应用。

## 资源限制与成本

资源限制直接关系到成本。设得太大，浪费资源、多花钱；设得太小，业务不稳定。资源优化的目标是用尽可能少的资源满足业务的稳定运行需求，这需要持续的监控和调整。在云环境下，资源就是钱，资源设置的精打细算能带来实实在在的成本节省。资源成本优化是容器运维的重要课题。

## 资源设置的实践建议

资源设置的实践建议可以总结为几条：基于实测数据而不是猜测；请求略高于平均使用、限制略高于峰值；定期回顾和调整；监控资源使用和限制的差距；对关键业务留足余量。这些建议的共同点是务实——资源设置不是一次性的精确计算，而是一个持续观察、持续调整的过程。

## GPU 资源限制

GPU 资源的限制和 CPU、内存不同，GPU 的调度和分配机制更复杂。GPU 通常不能像 CPU 那样按时间片切分，一个 GPU 往往只能被一个容器独占使用，所以 GPU 的调度更接近资源分配而非时间片调度。GPU 资源限制涉及 GPU 的分配、显存的管理、以及多容器共享 GPU 的场景。随着 AI 和机器学习负载的普及，GPU 资源的调度和限制成为容器平台的重要能力。GPU 的调度还要考虑拓扑亲和性——GPU 和 CPU、内存之间的连接关系会影响性能，所以高级的 GPU 调度会考虑 NUMA 拓扑。GPU 资源的限制，还涉及显存的管理：一个 GPU 的显存是有限的，多个容器共享一个 GPU 时，要分配各自的显存配额，防止某个容器占满显存影响其他容器。随着 AI 负载的普及，GPU 的资源调度和限制越来越重要，出现了专门的 GPU 调度方案（比如 GPU 虚拟化、MIG 多实例 GPU）。理解 GPU 资源限制的特殊性，是 AI 场景下容器平台能力的关键。

## 存储 IO 限制

存储 IO 的限制约束容器对磁盘读写的速率，防止某个容器的大量 IO 拖慢整个节点的存储。存储 IO 限制在数据库、日志处理这类 IO 密集的应用里尤为重要。IO 限制的实现通常基于 cgroup 的 blkio 子系统，可以设置读写速率的上限。存储 IO 限制的难点在于精确的计量和控制，不同存储后端对 IO 限制的支持程度不同。

## 网络带宽限制

网络带宽限制约束容器的网络出入速率。在共享网络的环境里，某个容器的大量网络传输会挤占其他容器的带宽，带宽限制能保障公平性。带宽限制通常在容器的网络接口上做流量整形。网络带宽限制和存储 IO 限制类似，都是资源隔离在 IO 维度的体现，对有大量数据传输的业务尤其重要。

## 资源的动态调整

资源的动态调整是指在容器运行过程中调整它的资源限制，以适应业务的变化。传统的资源限制是静态的，调整需要重启容器；动态调整能力（比如垂直扩缩容）可以在不重启的情况下调整 CPU 和内存的限制。动态调整能更好地应对业务的资源需求波动，但实现上涉及运行时的热更新，比较复杂。

## 多租户资源隔离

在多租户环境里，资源隔离是保障租户之间互不影响的关键。多租户资源隔离涉及几个层次：最基础的是 cgroup 层面的资源限制，保证单个容器不超用资源；往上是命名空间级别的资源配额，保证单个租户不超用配额；再往上是更细的 QoS 分级，保证关键租户的业务优先获得资源。多租户资源隔离的难点在于，既要隔离得彻底（租户之间互不干扰），又要资源利用率高（不能因为隔离而大量浪费）。这需要在隔离和效率之间做精细的权衡，通常的做法是按租户的重要性分级，关键租户优先保障，普通租户共享剩余资源。多租户资源隔离的实现，还要防止'噪声邻居'问题——一个租户的资源滥用（比如突然的 CPU 飙升、内存泄漏）不能影响其他租户。这需要硬性的资源上限（而不是只靠软性的权重），以及针对异常资源使用的检测和限流。多租户隔离的成熟度，直接决定了容器平台能不能安全地服务多个团队或客户。

## 资源限制与 SLA

资源限制和服务的 SLA（服务等级协议）密切相关。资源限制设得太紧，业务在高峰时资源不足，延迟上升，违反 SLA；设得太松，成本上升。所以资源限制的设置，要以 SLA 为依据——先明确业务的 SLA 要求（比如 P99 延迟、可用性），再反推需要多少资源。资源限制和 SLA 的关系，是把资源设置从'拍脑袋'变成'以目标为导向'的关键。

## 资源治理的总结

容器资源治理是一个系统工程，涵盖资源的设置、监控、调度、隔离和优化。它需要从单个容器的资源设置，到命名空间级配额，再到集群级的资源规划，层层递进。资源治理的目标，是让集群在稳定运行的前提下，尽可能高地利用资源、尽可能低地控制成本。做好资源治理，需要数据（监控）、工具（调度、配额）和流程（评审、调整）三者的配合。

## 资源限制与容器镜像的关系

资源限制和容器镜像看似无关，实则有关联。镜像的大小影响容器的启动和运行资源：镜像越大，拉取和解压消耗的资源越多，启动越慢；镜像里的应用依赖越多，运行时的内存占用也越大。所以资源优化要从两个层面一起看：镜像瘦身减少存储和启动资源，资源限制控制运行时的 CPU 和内存。一个镜像臃肿、又资源限制很紧的容器，往往会因为资源不足而频繁出问题。资源限制和镜像优化，是容器资源治理的两个侧面。

## 资源限制的监控告警

资源限制要配合监控和告警才能真正发挥作用。监控要关注：容器的实际资源使用和请求、限制的差距、节点的资源水位、以及资源使用异常（比如内存持续增长接近上限）。告警要设置合理的阈值，在资源接近限制、或节点资源紧张时提前通知，而不是等 OOM 或驱逐发生了才告警。资源限制的监控告警，是资源治理的'眼睛'，没有它，资源限制就是盲目的。

## 资源限制的未来趋势

容器资源限制的能力在不断演进。趋势之一是更细粒度的资源控制，从 CPU、内存扩展到 IO、网络、GPU 等更全面的资源；趋势之二是更智能的资源调度，基于历史使用数据预测资源需求、动态调整限制；趋势之三是资源限制和成本优化的结合，把资源使用精确地映射到成本，推动资源的高效利用。理解这些趋势，有助于把握容器资源管理的发展方向。

## 资源限制的最佳实践

资源限制的最佳实践可以总结为几条。第一，基于实测数据设置请求和限制，而不是拍脑袋——先不设限制跑一段时间，观察实际使用，再据此设置。第二，请求略高于平均使用、限制略高于峰值，留出余量应对波动。第三，内存限制要特别谨慎，设小了会 OOM，设大了失去意义。第四，定期回顾和调整，业务变化后重新评估资源设置。第五，监控资源使用和限制的差距，差距过大说明设置不合理。这些实践的核心，是让资源设置基于数据、持续调整，而不是一次设完就永远不改。

## 资源限制与成本

资源限制直接关系到成本，两者是紧密关联的。资源设置得过大，浪费了资源、多花了钱；设置得过小，业务不稳定，可能引发故障。在云环境下，资源就是钱，资源限制的精打细算能带来实实在在的成本节省。资源成本优化，通常从监控资源使用率和限制的差距入手，找出那些'申请了很多、实际用很少'的容器，调低它们的限制。资源限制与成本的关系，让资源优化不仅是技术问题，更是成本管理问题。

## 小结

容器资源限制的核心是理解请求和限制的区别、CPU 和内存的不同机制、以及调度和驱逐的运作。合理的资源设置，能让集群在利用率和稳定性之间取得平衡。
