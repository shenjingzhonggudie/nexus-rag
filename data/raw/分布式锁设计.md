# 分布式锁设计

## 为什么需要分布式锁

单机场景下用进程内的互斥锁就能保证临界区互斥，因为所有线程共享同一块内存。但服务部署到多台机器后，进程内锁失效，因为每个进程有独立的内存空间，锁不住别的进程。此时需要一把跨机器共享的锁来协调对共享资源的访问。分布式锁就是这样一个协调机制：多个进程通过一个共享的外部存储来竞争锁，谁抢到谁就能执行临界区。典型的场景包括：防止多台机器同时执行同一个定时任务、防止并发下单重复扣减库存、防止多实例同时处理同一批数据。

## 基于 Redis 的实现

最常见的分布式锁方案是 Redis 的 SET NX 命令：向 Redis 写入一个带唯一值的 key，只有写入成功的请求才获得锁。SET NX 是原子操作，多个请求同时写入时只有一个能成功，天然实现了互斥。释放锁时必须校验唯一值，只有持有者才能删除，防止误删别人的锁——如果 A 的锁过期了，B 抢到锁，此时 A 回来删除，若不校验唯一值就会删掉 B 的锁。唯一值通常是客户端生成的随机标识，释放时用 Lua 脚本保证校验和删除的原子性。这套方案简单高效，是最广泛使用的分布式锁实现。

## 过期时间与续期

锁必须设置过期时间，否则持有者崩溃后锁永远无法释放，造成死锁。但过期时间又引入新问题：业务执行时间可能超过过期时间，导致锁提前释放，此时其他请求抢到锁，两个请求同时进入临界区。解决思路是启动续期任务：业务未结束时持续刷新过期时间，让锁在业务执行期间一直有效。续期任务通常是一个后台线程或定时器，定期检查业务是否还持有锁，还在就延长过期时间。续期机制弥补了固定过期时间的缺陷，但也增加了实现的复杂度，要处理续期任务本身失效的情况。

## 基于 ZooKeeper 的实现

ZooKeeper 利用临时顺序节点实现分布式锁。所有竞争者创建临时顺序节点，序号最小的获得锁，其余监听前一个节点的删除事件。获得锁的客户端崩溃或断开连接后，它的临时节点会自动删除，下一个序号的客户端监听到删除事件后获得锁。ZooKeeper 锁天然支持失效回收，因为临时节点的生命周期和客户端会话绑定，这是它相比 Redis 锁的一大优势。但 ZooKeeper 锁的性能较低，因为每次竞争都要创建节点和注册监听，适合对一致性要求高、对吞吐要求不高的场景。

## Redis 与 ZooKeeper 的权衡

Redis 锁和 ZooKeeper 锁代表了分布式锁的两条路线。Redis 锁性能高、实现简单，但一致性弱——在极端情况下（如主从切换）可能出现锁丢失。ZooKeeper 锁一致性强、天然支持失效回收，但吞吐低、依赖 ZK 集群的稳定性。选型看业务对一致性和性能的侧重：扣库存、下单这类资金操作，即使性能稍差也要保证一致性，倾向 ZooKeeper 或带强一致保证的 Redis 集群；日志去重、防重复执行这类容错性高的场景，用 Redis 锁的高性能就够了。没有绝对的好坏，只有场景匹配。

## 死锁的防范

分布式锁的死锁主要来自锁持有者异常退出而锁未释放。防范手段首先是设置过期时间，让锁无论如何都会自动释放，这是兜底。其次是用唯一值校验，防止误删。再次是续期机制，避免锁在业务正常执行时提前过期。还有一点容易被忽视：锁的粒度要合理，锁的范围太大，持锁时间长，崩溃窗口大；锁的范围太小，又保护不了完整的临界区。设计时要让锁覆盖恰好需要互斥的操作，尽量缩短持锁时间，从根上降低死锁和锁竞争的概率。

## 锁的可重入性

可重入锁允许同一个持锁者在未释放锁的情况下再次获取同一把锁。在单机锁里可重入是常见需求，分布式锁里是否支持可重入要看实现。基于 Redis 的锁如果要支持可重入，需要在锁里记录持有者标识和重入次数，释放时递减计数，计到零才真正释放。不支持可重入的锁，业务代码里如果嵌套了两次获取同一把锁的操作，就会自己把自己锁死。是否支持可重入要在设计时明确，因为可重入性会显著增加实现复杂度，而很多业务场景其实用不到。

## 实践中的坑

分布式锁实践中有不少容易踩的坑。一是时钟问题：依赖过期时间的锁，对系统时钟敏感，各节点时钟不同步会导致过期判断失真。二是网络分区：持有者与锁存储之间网络断开，锁可能已经被释放而持有者不自知。三是锁的存储本身的可用性：Redis 或 ZooKeeper 挂了，锁机制就失效了。这些坑的根源是分布式环境的不可靠性，应对方法是接受分布式锁的不完美，在业务层做好幂等和兜底，把锁当作尽力而为的协调手段而非绝对保证。真正需要强一致的场景，应该考虑更重的方案如数据库约束或分布式事务。
