# RAGKit 总结报告

> 从零手搓的中文 RAG 系统 · 21 轮 · 268 条测试 · 版本 1.0.0

## 一、这是什么

一个**不使用任何 RAG 框架**、从零实现的中文检索增强生成系统。核心算法（BM25、RRF 融合、重排、拒答、评测指标）全部手写，默认模式**离线可运行、不需要 API Key、不联网**——用 hashing 字面级 embedding 作向量替身、抽取式回答作生成替身；真向量模型与 LLM 只作为可插拔适配器，留待将来接入。

**一句话定位**：不是"尽快得到一个能跑的仓库"，而是"能独立解释并重写每一个核心模块"。

## 二、最终成果

- **九层架构全贯通**：加载 → 分块 → 向量化 → 存储 → 检索 → 建库 → 生成 → API → 评测；
- **四个入口**：`ragkit build`（建库）/ `ask`（问答）/ `serve`（HTTP API）/ `eval`（评测）；
- **268 条契约测试**全绿，覆盖每一层的公开 API 与边界行为；
- **两套评测语料**：`data/`（后端分布式，100 篇 + 300 条手写 query）、`data2/`（机器学习，100 篇 + 300 条手写 query）——用跨领域验证结论的稳定性。

## 三、架构全景

| 层 | 职责 | 关键契约 |
|---|---|---|
| `loaders` | 文本加载 | `.txt/.md/.markdown`；UTF-8 + GBK 回退；坏文件隔离进 `failures` |
| `chunking` | 分块 | 固定大小 + overlap；`chunk_id` 由内容哈希生成（稳定） |
| `embeddings` | 向量化 | hashing 字面级；**L2 归一化责任在本层**（下游点积即余弦） |
| `stores` | 向量库 | 五文件落盘；`manifest.json` 最后写（崩溃时不留半成品） |
| `retrieval` | 检索 | BM25（idf）→ dense（点积）→ RRF 融合 → rerank 精排 |
| `index` | 建库 | `build` / `load_index`；`chunks.jsonl` 落盘 + id 一致性硬校验 |
| `generation` | 生成 | 证据→引用、拒答判定、抽取式回答；`openai_compatible` fail-fast |
| `api` | HTTP | `POST /ask`、`GET /healthz`；壳芯分离、错误翻译表 |
| `evaluation` | 评测 | recall@k / MRR 纯函数 + 评测编排 + 消融实验 |

**贯穿全项目的两条原则**：
1. **每层输出结构化对象，表现层各自翻译**——领域层产出 `Chunk`/`RetrievalResult`/`Answer`，CLI 翻译成文本、API 翻译成 JSON、评测读 `RetrievalResult`，互不耦合；
2. **测试即契约**——每个公开 API、每个边界行为都有测试锁定，改契约必改测试。

## 四、核心指标与消融结论

**评测基线**（100 篇语料 + 300 条手写 query）：`recall@1 = 0.833`、`MRR = 0.899`。

**消融实验**（4 组单变量对照，关掉某组件看退化多少）：

| 组 | recall@1 | MRR | 边际贡献 |
|---|---|---|---|
| baseline（全开） | 0.833 | 0.899 | — |
| **bm25_only** | **0.910** | **0.950** | BM25 腿 +0.000 |
| dense_only | 0.833 | 0.899 | **dense 腿 −0.08** |
| **no_rerank** | **0.910** | **0.948** | **rerank −0.08** |

**三个硬结论**：

1. **rerank 是负资产**（−0.08）。它用 dense 余弦精排，而 dense 是 hashing 字面级、不懂语义——精排等于"让字面级打分一票否决"，把 RRF 融合的互补性抹掉了。**默认已关闭**。
2. **dense 腿（hashing）在等权融合下是负资产**（−0.08）。hashing 把高频词（"数据库""容器"）当相似信号，在主题相邻的语料上分不清；BM25 的 idf 给罕见词（"脏读""雪崩"）高权重，能精准区分主题。
3. **最优是加权融合 α≈0.8**（recall@1=0.923）——给 dense 一个低权重（0.2）能贡献少量互补价值，略优于纯 BM25（0.913）；**最终落地 α=0.9**（BM25 权重 0.9 / dense 权重 0.1，两个数据集都接近最优的保守值）。

**关键的方法论发现**：
- **评测集太简单会测不出组件差异**（12 条时所有组满分，扩到 100 条 + 加误导文档后负贡献才现形）；
- **query 质量比规模重要**——"概念词 × 模板"合成的 query 与文档词汇重叠、指标虚高，手写自然语言 query 才暴露 dense 的真实弱点；
- **消融结论依赖语料特征**——加权融合的最优权重 α 在 data 上是 0.78、在 data2（ML 术语密集）上是 1.0，没有普适值，所以没把 weighted fusion 做成固定配置（那会是过度设计）。

## 五、关键设计决策（有代表性的几个）

1. **离线优先**：hashing embedding + 抽取式回答是"替身"，换来的是全程不联网、可复现、可控；真模型/LLM 留成可插拔适配器。这决定了整个项目的走向。
2. **配置对象进、领域对象出**：`search` 收 `RetrievalConfig`、`answer_question` 收 `LLMConfig`，而不是散参数。将来加字段不破坏签名（Pydantic 加字段已验证），散参数加一个就是破坏性变更。
3. **参数可注入 = 测试可隔离**：`main(argv, environ)`、`load_config(environ)` 不直接读 `sys.argv`/`os.environ`——测试时它们是 pytest 的、是真实环境，不是你的。判据：污染真实环境后照旧全绿。
4. **壳芯分离**：HTTP 的 `_answer_payload` 抽成纯函数可直调单测，handler 做薄到不值得测逻辑。拆分的第一判据是**可测试性**，不是"功能不同"。
5. **默认配置和数据结论一致**：消融证明 rerank 负贡献后，把 `rerank_enabled` 默认值改成 `False`——默认跑着已知更差的配置，等于交付一个错误的默认行为。

## 六、踩过的坑（提炼成规律）

1. **相对路径的基准是契约**：`doc_id` 是相对 build root 的路径，root 一变评测标注和索引全对不上——`data_dir` 必须指向语料目录本身，不是父目录。
2. **标识符唯一性要先于生成校验**：程序化生成语料时，误导文档标题与正文档标题重复会**覆盖**正文档——100 篇骤减到 43 篇才发现。
3. **配置违背意图要大声报错**：YAML 未知键被静默忽略（补 `extra="forbid"`）、`openai_compatible` 未实现却静默降级（改 `NotImplementedError`）——静默降级是最贵的失败模式。
4. **从模块导入同名符号会遮蔽子模块**：`from X.rerank import rerank` 让 `X.rerank` 变成函数，字符串路径解析失败——测试 patch 改用 `importlib.import_module`。
5. **复制粘贴残留**：同一段校验重复两遍、复制测试只改名字不改字段——改完要逐行过目。
6. **数据结构第一要义是表达语义**：`relevant` 用 `set` 不是"去重"，是"相关是无序成员关系"；`list` 会误导"有序可重复"。
7. **可再生的重建优于修补**：BM25 统计可从 chunks 重建，就不新增落盘格式；`data/index` 是产物（可随时重建）、`data/raw` 是原料（值得进版本控制）。
8. **事故的代价是没版本控制**："行尾 t 批量删除"误删大量代码，因为没有 git 提交无法回滚——教训是尽早提交。

## 七、技术债与演进方向（触发信号驱动）

| 项 | 触发信号 |
|---|---|
| 真语义 embedding（dense 腿重估） | 拿到 embedding 模型/API 时 |
| cross-encoder rerank | 接入真模型后重评 rerank |
| `openai_compatible` 真实生成 | 拿到 LLM API 密钥 + 网络可用 |
| 增量更新 | 全量重建实测慢到痛 |
| HTML/PDF 加载器 | 真实需要处理这些格式 |
| FastAPI 迁移 / 鉴权 | 真实部署需要 OpenAPI 文档或暴露公网 |
| 统计显著性检验 | 消融结论需要置信时 |

## 八、结语

这个项目的价值不在"跑通了一个 RAG"，而在**每一层都亲手实现、每一个决策都有数据支撑、每一个坑都变成了一条规律**。最硬的收获是消融实验教会的那件事：**没有数据，就没有"该不该有这个组件"的答案**——dense 腿和 rerank 是在"避免过度设计"和"实际需要"之间，被评测数据一锤定音的例子。

主线的终点是这里；而它真正的下一站，是拿到真 embedding 和 LLM 之后——把那些"负资产"在真实模型下重新评估，让系统从"字面级替身"走向"真语义"。
